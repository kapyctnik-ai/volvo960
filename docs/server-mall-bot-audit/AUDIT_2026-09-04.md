# Audit 2026-09-04 — findings, fixes applied, and what is still open

Read this together with `docs/HANDOFF_CLAUDE_CODE.md`. That file describes the
contract; this file describes what was found broken against it on commit
`6ff8992`, which of it is fixed in this change set, and what the next engineer
should do first. Every fix is marked in code with a comment starting
`AUDIT 2026-09-04 #<n>` where `<n>` is the finding number below, and every fix
has a regression test in `tests/test_audit_2026_09_regressions.py`.

How the audit was run: the configurator workbook is not in the repository, so a
synthetic `data/1.1 Configurator.xlsx` was generated (all 1110 catalog rows,
category-based fake costs, REF = 40% of NEW). Structural results (roles, BOM
lines, statuses, timings) are real; the euro figures in the examples are not.
Nothing below was verified against real purchase prices.

## Fixed in this change set

### #1 Non-English text produced a silently reduced, approvable plan — FIXED

`Нужен сервер Dell R760, 2 процессора Xeon 6430, 256 ГБ ОЗУ, 4 диска 1.92 ТБ SSD`
returned `COMPLETE`, `ready=True`: DIRECT had 1 CPU, 2x32 GB, no drives, no
deviation. The parser only knows English units and quantities; completion
filled the rest with defaults.

Fix: `new_path/service.py` — `contains_non_english()` (any Cyrillic letter)
short-circuits `_run` with `NON_ENGLISH_INPUT`; copy in `presentation/copy.py`.
Applies to first messages and to clarification answers.

Still open: the same failure mode exists for English text whose numbers the
parser does not understand (see #10, #11). A general "unparsed number with unit"
guard is the right next step: compare numbers+units found by a broad regex
against `ParseResult.extracted_fields` and ask instead of quoting when something
material was ignored.

### #2 Short clarification answers restarted the request — FIXED

`looks_like_full_rfq()` returned True for `Dell R760`, `256GB`, `64 GB`,
`Xeon Gold 6430`. `handle_clarification_answer` calls it before
`apply_clarification`, so answering a question with the thing the bot asked for
discarded the original RFQ. Now at least two independent specification signals
are required (model, CPU, RAM, storage, network, GPU, workload), or a long
workload description. `test_new_path_sticky_state_full_rfq_wins` still passes.

### #3 The planner blocked the Telegram event loop for 7–19 s — FIXED

Measured `process_text` on the synthetic workbook: 7.4 s, 8.1 s, 15.6 s,
18.9 s. Every other manager, and `/stop`, waited. `_plan_request` runs the
planner twice when the first pass is not COMPLETE, and `apply_manual_price`
rebuilds the planner and re-reads the workbook on every confirmed price.

Fix: `bot/handlers.py` runs `process_text`, `apply_clarification`,
`apply_manual_price` and `approve` through `asyncio.to_thread`;
`NewPathCPQService` serialises its public entry points with an `RLock`
because it holds mutable state (`_sessions`, planner rebuild). Throughput is
unchanged (one request at a time); responsiveness is fixed.

Still open: cache the parsed workbook across planner rebuilds; make the
planner a single pass with both pending modes.

### #4 Price entry mis-parsed and poisoned the price journal — FIXED

`_parse_price("1,250")` returned 1.25; `1,250.00` and `1.250,00` too. `$1 200`
was read as SKU `1` price 200. A new RFQ typed while a price was pending
(`Dell R760 8SFF, 2x Xeon 6430, 256GB RAM`) was read as price 7608 and offered
for confirmation. After `yes`, `journal.set_catalog_price` stores it by display
name, and `ManagerPurchaseDbSource` is the first price source, so the wrong
value outranks the workbook for every later quote. There is no undo.

Fix: `_normalize_number` handles thousands/decimal separators; `_parse_price`
accepts only price-shaped messages; `_parse_sku_and_price` requires a SKU token
containing a letter; `handle_manual_price` applies the same `looks_like_full_rfq`
guard as the clarification handler and starts a fresh request instead.

Still open: a `/prices undo` or expiry for manual prices, and `/sources`
showing who entered a manual price and when.

### #5 25GbE SFP28 could not be built anywhere — FIXED (parser) / PARTLY (catalog)

`parsing/extractors/network.py` alternation `sfp\+?|sfp28` matched `sfp` inside
`sfp28`, so media became `SFP+` and `nic_media_matches()` rejected every SFP28
card: `... 2x 25GbE SFP28` gave `engineering_candidates=0` on all 45 platforms,
Dell and HPE alike. Reordered to `sfp28|sfp\+?`.

After the fix HPE Gen11 builds DIRECT with 25GbE. Dell NEW platforms still have
no 25 GbE card: the four NEW 25G cards are HPE part numbers and are OEM-locked in
`compatibility_curation.yaml`; `Dell Mellanox ConnectX-4 CX422A Lx 2x25G SFP28
NDC` had no `speed_gb` because `catalog/labels.py` only matched `GB`, not `G`.
The label regex is fixed, but `resources/normalized_catalog.yaml` and
`catalog_attrs.yaml` are generated from the real workbook and could not be
regenerated here. Next engineer: run `scripts/build_catalog_attrs.py` and
`scripts/build_normalized_catalog.py` with the real workbook, verify the Dell
Mellanox row gains `speed_gb: 25`, then re-run
`Dell R760 8SFF, 2x Xeon Gold 6430, 256GB DDR5, 2x 25GbE` and expect at least a
DIRECT. `Mellanox ConnectX-4 Lx NIC (Dual-Port 25GbE SFP28)` has no form in its
label; add it via `component_attribute_overrides.yaml` with provenance if the
physical card is known.

Note that `compatibility_relations.yaml` contains 0 of 61 NICs; NIC
compatibility is form-factor only (`nic_forms` per family in
`compatibility_curation.yaml`) and never checks that a platform actually has a
free OCP3/NDC slot.

### #6 Missing workbook crashed the bot at startup with a traceback — FIXED (message only)

`create_dispatcher` builds `NewPathCPQService` unconditionally; its price
repository loads the workbook eagerly, so a missing/mistyped
`SERVERMALL_EXCEL_PATH` killed the process regardless of `CPQ_NEW_PATH_ENABLED`.
`main.run_bot` now exits with a clear message. The eager load itself is
unchanged.

Also related: CI (`.github/workflows/test.yml`) restores the workbook from a
secret; without it `test_e2_planner`, `test_e25_new_platforms`, `test_f2_e2e`,
`test_f1_completion_e2e`, `test_mvp_acceptance_corpus` and others fail rather
than skip. Ruff is not run in CI.

### #16 Docker build was broken — FIXED

`Dockerfile` copied a `templates` directory that does not exist. Removed, plus
the matching compose volume and `TEMPLATES_DIR`. Production runs under systemd;
the Docker path is untested beyond building.

### #14 (partial) Stale user-facing copy — FIXED

`/start` and `/quote` described "Exact / Alternative / REF" and PDF/DOCX/XLSX
upload. Both now describe plain-text input and DIRECT / ALTERNATIVE / VALUE.

## Found, not fixed — ordered by impact

### #7 NEW quotes contain REF drives without a deviation

All 62 `storage` rows in `normalized_catalog.yaml` carry `condition: REF`. A NEW
DIRECT for `4x 1.92TB SAS SSD` uses `cmp_storage_1920_0_sas_sff_4b05479fc7`
(REF) with no deviation, and the client proposal shows it next to `(NEW)` lines.
Either the workbook has NEW drives that the catalog builder tags as REF, or the
builder must add a `ref_component_in_new_build` deviation. Decide with the
business owner; handoff §14 says NEW must not silently receive REF.

### #8 DIRECT omits tray caddies that ALTERNATIVE and VALUE include

Same request: DIRECT (R760, 4 drives) has no tray line, ALTERNATIVE (DL360
Gen11) and VALUE (R6525) have 4 each. `d1/builder.py` adds trays only when
`get_compatible_trays` returns something, so missing tray data silently means
"no trays needed". Either DIRECT is under-quoted or the others are
over-quoted. Suggested: when drives are present and no compatible tray exists,
emit the platform-scoped `pending:tray:...` line the handoff §6 describes,
rather than nothing.

### #9 NVMe RAID10 on R760 8SFF is reported as a catalog gap

`Dell R760 8SFF NEW, 2x Xeon Gold 6430, 256GB DDR5, 4x 1.92TB NVMe RAID10`:
`fully_priced_candidates=4, post_diversity_candidates=0` → NO_VALID_OPTIONS.
Four built and priced candidates are discarded by the diversity filter in
`planning/planner.py`. The filter should degrade to two roles (DEGRADED), not to
nothing. Reproduce with the probe in the audit report.

### #10 Workload defaults produce commercially implausible CPUs

`Need a virtualization server, 512GB RAM, 20TB usable SSD, 2 CPUs` → DIRECT
2x Xeon Bronze 3408U (8C), VALUE 2x Xeon Silver 4112 (4C). The virtualization
profile in `resources/workload_profiles.yaml` sets `default_min_cpu_cores=8`
per server and the planner takes the cheapest CPU above the floor. Add
per-workload cores-per-socket and minimum tier floors.

### #11 Quoting with no requirements

`need a server` → question → `I don't know` → full COMPLETE plan on R760xs. A
non-answer to the only critical question should block, not proceed with
defaults. See `clarification/policy.py` handling of an unrecognised answer.

### #12 Production host, root user and password SSH in a public repo

`deploy/deploy.py:21-22` hard-codes `HOST`, `USER = "root"`, password from
`DEPLOY_SSH_PASSWORD`, `paramiko.AutoAddPolicy()`; same in 11 other scripts
under `deploy/` and `scripts/`. No token or password was found in the tree or
in the last 50 commits, but the handoff says credentials were shared in the
project history. Move host/user to env, switch to key auth, pin the host key,
disable root password login, rotate the password.

### #13 FSM state is in-memory

`Dispatcher()` uses MemoryStorage; `request_id`, `pending_prices` and price
confirmations vanish on every restart/deploy. New-path sessions are persisted
in the journal, so a SQLite/Redis FSM storage (or re-attaching the last draft
session per chat on `/prices` and `/approve`) would close the gap.

### #14 Production flag defaults off; README describes the legacy product

`CPQ_NEW_PATH_ENABLED` defaults to false in `config.py` and `.env.example`
while the handoff calls the new path production. A fresh environment or a lost
`.env` silently runs `simple/` (files, OCR, different logic). Flip the default
or refuse to start without an explicit value; rewrite README.

### #15 `APP_ENV` defaults to development, which opens the bot to everyone

`bot/access.py`: an empty allowlist admits all users unless `APP_ENV` is
`production`/`prod`. `/sources` exposes purchase prices. Consider making the
allowlist mandatory whenever a bot token is set, and not replying to
unauthorised users at all.

### #17–#23 Smaller items

- `_safe_process` sends raw exception text to the chat.
- `FX_USD_EUR=0.92` is a fixed env value with no date; manual prices are USD,
  display is EUR.
- Catalog labels contain Cyrillic letters (`Caсhe` in Xeon Silver 4112) and
  prices (`... 1440eur`); `T160` is categorised as an accessory from an
  `Extra 1` row, which is why the planner sees no T160.
- CI runs only on `main`, no Ruff, full suite ≈ 3 h.
- `tests/test_channel_rfqs.py:21` contains a real-looking email at a real
  domain; confirm it is fictitious.
- `simple/`, `shadow/`, `extraction/`, `models/` and the pdf/docx/ocr
  dependencies are legacy-only.
- Logs carry no `user_id`/`request_id` correlation.
